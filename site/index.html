Hand an agent a ticket and it opens a layout. The request never became a problem anyone could argue with.

This suite is the missing middle. The agent inspects the current product, tags what is known versus assumed, and writes a brief you can reject. Mechanism and craft wait until that brief is specific enough to be wrong.

/product-define

Names what is uncertain and which phases would change a decision. It proposes a plan and waits. A skip has to come with a reason.

/product-frame

Writes the problem from the codebase and the live product. A feature request does not pass through intact.

How much runs

The orchestrator sizes the route to the uncertainty. A clear change to a known table gets patterns, flow, craft, and a QA pass. When the problem is understood and the mechanism is not, it frames first and storms options. Fuzzy or high-stakes work also tests the assumption most likely to kill the idea.

If the mechanism is already chosen, it skips the storm and says why. PROCEED WITH ASSUMPTION is a normal gate.

What lands in the repo

problem.md, model.md, design/sweep/board.html, and a one-page context.md every phase updates. Craft stays in whatever system you already use.

Questions

Do I run every phase every time?

No. The orchestrator skips anything that does not reduce a named uncertainty, and it has to say why.

Does this replace my design system?

No. This suite decides why something exists and how it works. Expression is a plug-in: Linear, Ramp, better-ui, your tokens.

Will it work on a feature we already shipped?

Yes, if the diagnosis is honest. Inspection starts with the codebase and current behavior. Critique mode is the entry when something already live feels off.
