# Problem brief — cold-readable `problem.md`

A stakeholder reads this in five minutes. Argument first; tables support. Follow this order; do not ship a form stack.

## Skeleton

```markdown
# Problem — <short name>
Updated: <date> · by design-frame

## TL;DR
**Problem:** <one-sentence problem statement>
**Desire:** <one line — feel / become>
**Why it matters:** <the one number or consequence that proves urgency>

## Sandbox
| Materials / brand | … |
| Platform / system | … |
| Complexity budget | … |
| Non-negotiables | … |

## Aging
<one line — 100th use / year two>

## Current state
<Mermaid: actor workflow with ⚡ frictions, and/or artifact map>

## Evidence (strongest 3–5)
- [Observed|Measured|Reported] … (denominators on Measured/Reported)

## Decomposition
| Part | Content |
|---|---|
| Actor | … |
| Situation | … |
| Goal | … |
| Friction | … |
| Consequence | … |
| Workaround | … |
| Desired change | … |
| Desire | … |

## Problem statement
*<Actor> doing <situation> must <goal>, but <friction>, forcing <workaround/consequence>.*
(Mark Assumed clauses inline.)

## Non-goals
1. … — because …
2. …

## Product principles
1. …
2. …

## Success signals
- **Primary:** …
- **Confirming:** …
- **Guardrails:** …

## Open questions
- …
```

## Rules

- TL;DR stands alone — Desire beside pain.
- Sandbox and Aging before the diagram — concepting reads them first.
- Diagrams show **today** with ⚡, never the aspirational future.
- Every evidence line carries a tag; Measured/Reported carry denominators.
- Non-goals with reasons; principles violable and specific.
